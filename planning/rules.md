# 계획서 작성 규칙 (plan)

이 프로젝트의 모든 신규 개발 계획서는 이 규칙을 따릅니다.

## 개정이력

- **2026-10-15 최초 수립.** 파일 이름 규칙, 헤딩 7개 고정(배경·개요·필요한 조치·조치에 대한 설명·수정 범위·리스크·Phase별 할 일), Phase 1 첫 할 일은 브랜치 생성으로 정했습니다(720f5de).
- **2026-10-29 문서 구조와 작성 원칙 개정.** 케빈님이 녹아웃 대진 전송 점검 계획서를 직접 첨삭하면서, 계획서가 사람이 읽기 어렵고 우리끼리 만든 말이 많다는 문제가 드러나 고쳤습니다.
  - **문서 구조:** 헤딩 7개를 9개 장(배경 및 목적·개선 사항 요약·개선 상세·수정 범위·테스트 계획·리스크 및 대응 방안·단계별 실행 계획·완료 기준·참고 자료)으로 바꿨습니다. 해당 없는 장도 지우지 않고 「해당 없음」과 이유를 씁니다.
  - **배경 및 목적:** 비개발자도 이해할 수 있는 평문으로만 씁니다. 코드 경로·함수 이름·커밋 해시·설정값은 본문에 `[n]` 번호만 달고, 9장 참고 자료에 모읍니다.
  - **개선 사항 요약:** 항목마다 「문제가 있어서, 조치합니다」 한 문장으로 씁니다. 저장소에 반영할 변경만 넣고, 운영 확인·수동 점검·승인은 7장으로 보냅니다.
  - **개선 상세:** 현재 동작·문제점·변경 내용·예외 처리·검증 방법·근거를 기준으로 쓰고, 확인·추정·미확인을 나눠 적습니다.
  - **테스트 계획·완료 기준 신설:** 테스트 구성·주요 시나리오·통과 기준을 따로 두고, 테스트 통과와 계획 전체 완료를 구분합니다.
  - **통제 절차 신설:** 계획 변경 관리, 실행 및 승인 통제(승인 표), 검증 및 결과 기록, Phase 전환 규칙을 더했습니다. 브랜치 생성·전환과 커밋은 승인 예외로 두었습니다.
  - **헤더·용어:** 헤더는 짧은 명사구로 씁니다. 유닛 테스트·회귀 테스트·payload·mock 같은 개발 표준어를 쓰고, 「몸통」「시험」「고정」 같은 임의 번역어는 쓰지 않습니다.
  - **작성 전후 확인 사항 신설:** 14개 항목 체크리스트로 내보내기 전에 점검합니다.
  - **시각 명령 수정:** `TZ=Asia/Seoul date` 는 이 PC 의 Git Bash 에 시간대 자료가 없어 UTC 로 나왔습니다(20:55 KST 에 11:55 GMT). `TZ=KST-9 date` 로 바꿨습니다.
  - **스킬 이름 변경·전역 승급:** 계획서 스킬을 `pln` 에서 `planning` 으로 바꾸고 이 규칙에 맞게 고쳤습니다. 모든 프로젝트에서 쓰도록 전역 스킬(`~/.claude/skills/planning/`)로 옮기고 저장소의 프로젝트 스킬은 지웠습니다. 전역 스킬은 프로젝트에 이 파일이 있으면 이 파일을, 없으면 스킬 폴더의 `rules.md`(이 파일 사본)를 따릅니다.
  - **본보기 제거:** 녹아웃 계획서를 본보기로 지정했다가 뺐습니다. 그 계획서는 이 규칙으로 다시 씁니다.

전역 `planning` 스킬(`~/.claude/skills/planning/SKILL.md`)은 이 규칙을 읽고 계획서를 작성합니다.

**핵심 원칙**

1. 코드 작성·수정 전에 반드시 계획서를 작성합니다.
2. 계획서에 명시되지 않은 코드 변경은 하지 않습니다.
3. 확인한 사실과 추정, 미확인 사항을 구분합니다.
4. 계획의 변경과 실행은 승인 범위를 준수합니다.
5. 작업 완료 여부는 실제 검증 결과를 근거로 판단합니다.

## 1. 파일 위치와 이름

형식: `plans/yyyymmdd_hhmmss_계획서명.md`

예시: `plans/20261015_213000_VLM판독.md`

- 시각은 계획서 작성을 시작한 시각(KST)으로 합니다.
- 시각은 `TZ=KST-9 date +%Y%m%d_%H%M%S`로 얻습니다. `TZ=Asia/Seoul`은 이 PC의 Git Bash에 시간대 자료가 없어 UTC로 나오므로 쓰지 않습니다.
- 계획서명은 한국어로 짧고 명확하게 작성하며 띄어쓰기를 사용하지 않습니다.
- 동일한 주제의 계획서라도 별도 작업이면 새로운 파일을 작성합니다.
- 기존 계획서는 파일명을 변경하지 않습니다.
- 진행 중인 계획의 변경은 원칙적으로 기존 파일에 반영하고, 변경 내용과 사유를 기록합니다.

## 2. 문서 구성

모든 계획서는 다음 9개 장을 **지정된 순서와 이름 그대로** 작성합니다.

문서 제목(`#`)은 계획서명으로 합니다. 제목 바로 다음은 `## 1. 배경 및 목적`입니다.

작성 시각, 작성 경위, 규칙 파일 안내 등의 머리말은 넣지 않습니다.

**표준 목차**

- `## 1. 배경 및 목적`
- `## 2. 개선 사항 요약`
- `## 3. 개선 상세`
  - `### 3.1 개선 항목명`
  - `### 3.2 개선 항목명`
  - `### 3.n 개선 항목명`
- `## 4. 수정 범위`
  - `### 4.1 수정 대상 및 영향 범위`
  - `### 4.2 작업 제외 범위`
- `## 5. 테스트 계획`
  - `### 5.1 테스트 구성`
  - `### 5.2 주요 테스트 시나리오`
  - `### 5.3 통과 기준`
- `## 6. 리스크 및 대응 방안`
- `## 7. 단계별 실행 계획`
  - `### Phase 1. 작업명`
  - `### Phase 2. 작업명`
  - `### Phase n. 작업명`
- `## 8. 완료 기준`
- `## 9. 참고 자료 (References)`

**각 장의 책임**

| 장 | 작성 내용 |
|---|---|
| 1. 배경 및 목적 | 현재 문제와 개선 목적 |
| 2. 개선 사항 요약 | 문제와 조치를 한 줄씩 정리 |
| 3. 개선 상세 | 현재 동작, 변경 내용, 근거 |
| 4. 수정 범위 | 변경 대상과 영향, 제외 범위 |
| 5. 테스트 계획 | 테스트 구성, 시나리오, 통과 기준 |
| 6. 리스크 및 대응 방안 | 예상 위험과 대응 |
| 7. 단계별 실행 계획 | 실제 수행 순서와 확인 절차 |
| 8. 완료 기준 | 계획 전체의 종료 조건 |
| 9. 참고 자료 | 판단에 사용한 근거 |

**구성 원칙**

- 9개 장의 순서와 이름은 변경하지 않습니다.
- 해당 사항이 없는 장은 삭제하지 않고, '해당 없음'과 그 이유를 간결하게 작성합니다.
- 필수 하위 제목 외에는 필요한 항목만 추가합니다.
- 내용이 없는 표나 불필요한 그림을 만들지 않습니다.
- 동일한 내용을 여러 장에서 반복하지 않습니다.
- 문서의 일관성은 유지하되 분량을 채우기 위한 설명은 작성하지 않습니다.

## 3. 장별 작성 원칙

### 3.1 배경 및 목적

- 현재 어떤 문제가 있는지 설명합니다.
- 이 계획으로 무엇을 해결할지 명확히 작성합니다.
- 개발자가 아닌 사람도 이해할 수 있는 평문으로 작성합니다.
- 코드 경로, 함수 이름, 커밋 해시, 설정값을 사용하지 않습니다.
- 확인하지 못한 문제는 발생한 사실처럼 단정하지 않습니다.
- 기술적 해결 방법보다 문제와 목적을 먼저 설명합니다.

### 3.2 개선 사항 요약

- 번호 목록으로 작성합니다.
- 항목마다 **'문제가 있어서, 조치합니다'** 형식의 한 문장으로 작성합니다.
- 실제 저장소에 반영할 변경 사항만 포함합니다.
- 코드, 설정, 테스트, 데이터 구조, 스크립트 변경 등을 포함할 수 있습니다.
- 운영 확인, 수동 점검, 승인 등의 활동은 포함하지 않고 7장에 작성합니다.
- 구현 세부 사항과 파일 경로는 작성하지 않습니다.
- 3장의 개선 항목과 번호 및 순서를 일치시킵니다.

**예시**

1. 팀이 확정되지 않은 경기도 전송될 수 있어서, 팀 미정 경기를 전송 대상에서 제외합니다.
2. 이전 시즌 경기가 일정에 포함될 가능성이 있어서, 해당 경기를 제외하는 회귀 테스트를 추가합니다.

### 3.3 개선 상세

2장의 각 개선 항목을 같은 번호로 설명합니다.

각 항목은 다음 내용을 기준으로 작성합니다.

- **현재 동작:** 현재 코드에서 확인한 동작이나 상태
- **문제점:** 현재 동작이 요구사항과 다른 부분
- **변경 내용:** 수정하거나 추가할 동작 및 테스트
- **예외 처리:** 경계 조건, 실패 상황, 재시도 등이 필요한 경우
- **검증 방법:** 변경 결과를 확인하는 방법
- **근거:** 판단에 사용한 코드·문서 등을 `[n]`으로 표시

단, 실제로 필요하지 않은 항목까지 형식적으로 채우지 않습니다.

**근거 작성 원칙**

- 직접 확인한 코드와 자료만 확정된 사실로 작성합니다.
- 추정과 미확인 사항은 그 상태를 명시합니다.
- 실제 코드와 다른 동작을 현재 동작으로 작성하지 않습니다.
- 확인하지 않은 코드의 동작을 임의로 추론하지 않습니다.
- 함수나 코드의 동작을 설명하는 경우 확인한 근거를 남깁니다.
- 본문에는 `[n]`을 사용하고 상세 출처는 9장에서 관리합니다.

**확인 상태의 구분**

- **확인:** 실제 코드, 문서, 로그 또는 테스트 결과로 확인했습니다.
- **추정:** 확인한 정보를 토대로 가능성을 판단했지만 검증하지 않았습니다.
- **미확인:** 필요한 정보가 없거나 확인 작업을 수행하지 못했습니다.

추정을 확인된 사실처럼 작성하지 않습니다.

### 3.4 수정 범위

**4.1 수정 대상 및 영향 범위**

수정하거나 새로 생성하는 파일과 그 영향을 표로 작성합니다.

권장 열: 파일 경로 / 변경 구분 / 변경 내용 / 영향 범위

- 변경 구분은 추가·수정·삭제로 작성합니다.
- 실제 확인된 경로를 사용합니다.
- 예상 경로는 예상임을 표시합니다.
- 기존 기능에 영향을 주는 경우 관련 범위를 명시합니다.
- 계획에 없는 파일 변경이 필요하면 계획 변경 절차를 따릅니다.

**4.2 작업 제외 범위**

- 이번 계획에서 하지 않는 작업을 명시합니다.
- 관련성이 있지만 의도적으로 제외한 작업을 우선 작성합니다.
- 제외한 작업을 진행 중 임의로 추가하지 않습니다.
- 추후 작업이 필요하면 별도 계획으로 분리하거나 변경 승인을 받습니다.

### 3.5 테스트 계획

**5.1 테스트 구성**

- 테스트 파일과 디렉터리 구조를 트리로 작성합니다.
- 기존 파일과 신규 파일을 구분합니다.
- 테스트의 목적과 대상을 설명합니다.
- 신규 테스트 파일이 없다면 기존 테스트의 활용 범위 또는 테스트 파일이 필요 없는 이유를 작성합니다.

**5.2 주요 테스트 시나리오**

테스트 시나리오를 표로 작성합니다.

권장 열: 테스트 케이스 / 입력·조건 / 기대 결과 / 검증 대상

- 정상 동작과 주요 예외 상황을 포함합니다.
- 회귀 위험이 있다면 회귀 테스트를 포함합니다.
- 외부 시스템에 의존하는 동작은 mock 사용 여부를 명시합니다.
- 실제 운영 환경에서만 확인 가능한 사항은 7장의 운영 검증으로 분리합니다.

**5.3 통과 기준**

- 무엇을 만족해야 테스트가 통과한 것인지 작성합니다.
- 테스트 수, 성공·실패 조건, 검증할 동작 등을 가능한 범위에서 명확히 합니다.
- 정량적 기준이 필요하면 측정 가능한 수치를 사용합니다.
- 임의로 성공률이나 성능 수치를 만들어내지 않습니다.
- 테스트 통과와 실제 운영 검증 완료를 혼동하지 않습니다.

### 3.6 리스크 및 대응 방안

리스크 / 영향 / 대응 방안을 표로 작성합니다.

- 변경으로 인해 기존 기능이 영향을 받을 가능성을 검토합니다.
- 외부 API, 일정, 데이터 상태, 환경 차이 등의 의존성을 고려합니다.
- 확인된 위험과 예상 위험을 구분합니다.
- 대응 방법을 구체적으로 작성합니다.
- 확인되지 않은 위험을 확정된 문제로 표현하지 않습니다.

### 3.7 단계별 실행 계획

전체 작업을 실제 수행 순서에 따라 Phase로 구분합니다.

- 각 Phase는 `### Phase 1. 작업명` 형식으로 작성합니다.
- 날짜가 정해진 Phase는 제목 끝에 `(11/01)`처럼 표시합니다.
- 실제 실행할 작업은 체크박스로 작성합니다.
- 작업 순서에 의존성이 있으면 앞선 작업의 완료 조건을 명시합니다.
- 구현, 테스트, 운영 검증, 승인 단계를 구분합니다.
- 각 Phase의 완료 여부를 판단할 수 있도록 검증 항목을 포함합니다.
- 흐름 설명이 필요한 경우 Mermaid를 사용합니다.

**Phase 1 규칙**

- 첫 번째 실행 작업은 반드시 브랜치 생성입니다.
- 브랜치 이름과 파생 기준은 `~/.claude/rules/git.md`를 따릅니다.
- 브랜치 생성은 승인 예외입니다(5장). 계획서 승인 전에 만들어도 되지만, 코드 변경은 승인 뒤에 합니다.
- 브랜치 생성 전에는 계획 수립과 허용된 읽기·분석 작업만 수행합니다.

**마지막 Phase 규칙**

마지막 Phase는 다음 순서로 마무리합니다.

1. 전체 변경 사항과 검증 결과 확인
2. 완료 기준 충족 여부 확인
3. 커밋 메시지 초안 작성
4. 케빈님 최종 승인 대기
5. 승인 후 `finish` 수행

`finish`는 프로젝트에 정의된 절차에 따릅니다. 정의되지 않았다면 실행하지 않고 확인을 요청합니다.

**진행 기록**

- 실제 완료한 작업만 체크합니다.
- 수행하지 않은 작업이나 실패한 검증은 완료로 표시하지 않습니다.
- 수행 결과가 중요한 경우 체크박스 아래에 결과를 기록합니다.
- 기록에는 필요한 경우 실행 시각, 테스트 수, 성공·실패 수, 관련 커밋을 포함합니다.
- 실패하거나 보류된 작업은 원인과 현재 상태를 기록합니다.

### 3.8 완료 기준

계획 전체를 완료했다고 판단할 수 있는 조건을 작성합니다.

- 핵심 개선 사항의 구현 완료
- 필요한 테스트의 통과
- 주요 회귀 문제의 부재 확인
- 필요한 운영 검증 완료
- 합의된 제외 범위 준수
- 승인 및 마무리 절차 완료

위 항목은 해당 계획에 필요한 것만 구체화합니다.

**완료 판정 원칙**

- 테스트가 통과했다고 계획 전체가 완료된 것은 아닙니다.
- 운영 검증이 필요한 경우 해당 검증까지 완료해야 합니다.
- 검증하지 못한 항목이 있으면 완료로 단정하지 않습니다.
- 완료 기준을 충족하지 못한 경우 미완료 사유와 남은 작업을 명시합니다.
- 완료 기준을 사후에 완화하려면 변경 승인을 받습니다.

### 3.9 참고 자료 (References)

3장 등 본문에서 사용한 `[n]` 번호를 순서대로 정리합니다.

참고 자료에는 필요에 따라 다음 정보를 기록합니다.

- 파일 경로 및 관련 함수·코드 위치
- 관련 문서 및 작업 이름
- 커밋 해시
- 테스트 결과 또는 로그 위치
- 외부 문서의 제목 및 URL

**작성 원칙**

- 참조 번호는 문서 전체에서 일관되게 사용합니다.
- 존재하지 않는 파일, 커밋, 실행 결과를 생성하지 않습니다.
- 가능한 한 실제 확인한 위치까지 구체적으로 기록합니다.
- 참조 대상이 변경되어 근거가 달라졌다면 함께 갱신합니다.
- 같은 근거는 기존 번호를 재사용합니다.

## 4. 계획 변경 관리

**계획에 없는 변경은 먼저 계획을 수정하고 승인받습니다.**

구현 중 새로운 문제나 변경 필요성이 발견되면 다음 절차를 따릅니다.

1. 계획 범위를 벗어나는 코드 변경을 중단합니다.
2. 발견한 문제와 근거를 확인합니다.
3. 기존 계획에 미치는 영향을 분석합니다.
4. 관련 개선 항목, 수정 범위, 테스트 및 Phase를 갱신합니다.
5. 변경 사유와 영향을 케빈님께 보고합니다.
6. 승인을 받은 뒤 변경된 범위의 작업을 진행합니다.

**변경 관리 원칙**

- 단순 오탈자, 표현 정리, 진행 결과 기록은 별도 승인 없이 수정할 수 있습니다.
- 구현 범위, 동작, 테스트 기준, 완료 기준의 실질적 변경은 승인 대상입니다.
- 계획을 수정했다는 이유만으로 실행 승인이 생기지 않습니다.
- 승인되지 않은 변경을 다른 작업에 묶어 적용하지 않습니다.
- 계획 변경 이력은 문서에 간결하게 기록하되, 표준 목차를 추가하거나 변경하지 않습니다.
- 변경 이력은 관련 항목 또는 7장에 변경 일시·사유·승인 여부를 기록합니다.

새로운 요구사항이 기존 계획의 목적과 크게 다르면 별도 계획서를 작성합니다.

## 5. 실행 및 승인 통제

**계획서 작성과 실제 실행은 구분합니다.**

계획에 작업이 기재되어 있어도 해당 작업이 자동으로 승인된 것은 아닙니다.

**기본 승인 기준**

| 작업 구분 | 기본 원칙 |
|---|---|
| 파일 읽기·검색·분석 | 허용 |
| 계획서 최초 작성 | 허용 |
| 계획서 진행 기록 | 허용 |
| 브랜치 생성·전환 | 허용(예외) |
| 코드·설정·테스트 파일 변경 | 실행 승인 필요 |
| 테스트·빌드·스크립트 실행 | 승인 정책 확인 |
| 패키지 설치·환경 변경 | 승인 필요 |
| 커밋 | 허용(예외) |
| 푸시·배포 | 명시적 승인 필요 |
| 데이터 삭제·파괴적 작업 | 명시적 승인 필요 |

브랜치 생성·전환과 커밋은 예외로 승인 없이 합니다(케빈님 2026-10-29). Phase 1 의 feature 브랜치 생성, 녹화 전에 develop 으로 돌리는 것, 계획서·보고서 문서 커밋이 여기에 들어갑니다. 푸시와 develop·main 으로의 finish 는 여전히 승인을 받습니다.

상위 규칙이나 사용자가 이미 명시적으로 허용한 작업은 해당 승인 범위를 따릅니다. 승인된 범위를 임의로 확대하지 않습니다.

**승인 원칙**

1. 승인 요청에는 수행할 작업과 영향을 명확히 설명합니다.
2. 한 번에 승인받은 작업 범위는 별도 재승인 없이 수행할 수 있습니다.
3. 승인 범위를 벗어나는 작업은 추가 승인을 받습니다.
4. 거절되거나 승인되지 않은 작업은 실행하지 않습니다.
5. 승인 여부가 불명확하면 임의로 허용된 것으로 판단하지 않습니다.

승인이 필요한 Phase 항목에는 `(허락 필요)`를 표시합니다.

계획서에 `(허락 필요)`를 적는 것은 승인 요청의 표시일 뿐, 승인을 의미하지 않습니다.

## 6. 검증 및 결과 기록

**실행하지 않은 작업을 실행했다고 쓰지 않습니다.**

- 테스트를 실행하지 않았으면 '미실행'으로 기록합니다.
- 실행 결과를 확인하지 못했으면 '결과 미확인'으로 기록합니다.
- 테스트 일부만 성공했으면 전체 통과로 표현하지 않습니다.
- mock 테스트 결과를 실제 운영 환경 검증 결과로 표현하지 않습니다.
- 코드 분석을 통한 예상 결과와 실제 실행 결과를 구분합니다.
- 실행 오류가 발생하면 오류 내용과 확인 가능한 원인을 기록합니다.
- 검증 결과는 실제 출력, 로그, 테스트 결과 등을 근거로 작성합니다.

**기록할 정보**

필요에 따라 다음 내용을 남깁니다.

- 실행한 명령 또는 작업
- 실행 시각 및 환경
- 성공·실패한 테스트 수
- 주요 검증 결과
- 실패 원인 및 후속 조치
- 관련 커밋 및 로그

검증 기록은 관련 Phase 항목 아래에 작성합니다.

**Phase 전환 규칙**

- 이전 Phase의 필수 완료 조건을 충족한 뒤 다음 Phase로 진행합니다.
- 이전 Phase의 실패가 다음 Phase에 영향을 주면 진행을 중단합니다.
- 일정 또는 외부 조건 때문에 실행할 수 없는 Phase는 보류 상태로 기록합니다.
- 필수 검증을 건너뛰려면 사유와 영향을 보고하고 승인을 받습니다.
- 보류·생략된 검증을 성공한 것으로 간주하지 않습니다.

## 7. 헤더 및 시각화 규칙

**헤더**

- 짧고 명확한 명사구로 작성합니다.
- 같은 계층의 헤더는 표현 형식을 통일합니다.
- 불필요한 부연 설명을 헤더에 넣지 않습니다.
- '적용되는 개선에 대한 설명'과 같은 문장형 제목을 피합니다.
- Phase 제목은 `### Phase 1. 작업명` 형식을 따릅니다.
- 날짜가 정해진 Phase는 `(11/01)` 형식으로 표시합니다. 연도가 모호할 수 있으면 연도도 명시합니다.

**그림**

- 파일과 모듈의 포함 관계는 트리형 코드 블록으로 표현합니다.
- 처리 흐름과 구성 요소 사이의 관계는 Mermaid로 표현합니다.
- 흐름은 `flowchart`를 사용합니다.
- 시간 순서의 상호작용은 `sequenceDiagram`을 사용합니다.
- 현재 구현과 변경 계획을 함께 나타내는 경우 계획 부분을 점선 또는 `(계획)`으로 구분합니다.
- 그림과 본문이 서로 다른 동작을 설명하지 않도록 확인합니다.
- 설명에 도움이 되지 않는 그림은 작성하지 않습니다.

## 8. 용어 및 문체 규칙

헌법의 휴머니즘 리포트(`~/.claude/rules/HUMANISM_REPORT.md`)를 따릅니다.

**문체**

- 계획서 설명 문장은 `~합니다` 체로 통일합니다.
- 결론을 먼저 작성하고 필요한 근거를 뒤에 배치합니다.
- 한 문장에는 가능한 한 하나의 핵심 내용을 담습니다.
- 불필요한 수식어와 반복 설명을 제거합니다.
- 수치로 설명할 수 있는 내용은 가능한 한 정량적으로 작성합니다.
- 확인되지 않은 수치를 임의로 생성하지 않습니다.
- 줄표(`—`)를 사용하지 않습니다.
- 표는 4열 이하로 작성합니다.

**용어**

- 개발 분야에서 일반적으로 사용하는 표준 용어를 사용합니다.
- 유닛 테스트, 회귀 테스트, payload, mock, dryRun 등 실제 개발 용어를 사용합니다.
- '몸통', '시험', '고정'과 같이 기술적 의미가 모호해지는 임의 번역은 피합니다.
- 동일한 개념은 문서 전체에서 같은 용어로 표현합니다.
- 비개발자가 이해해야 하는 부분에서는 전문 용어보다 동작과 목적을 설명합니다.

**사실 표현**

- 직접 확인한 사실과 추정을 명확하게 구분합니다.
- 모르는 내용은 모른다고 작성합니다.
- 확인하지 못한 내용은 1인칭으로 확인하지 못했다고 밝힙니다.
- 추정한 내용을 확정적으로 표현하지 않습니다.
- 실제 확인한 자료에 근거하지 않은 성공·완료·정상 동작 표현을 사용하지 않습니다.

## 9. 작성 전후 확인 사항

계획서 작성이 끝나면 다음 사항을 점검합니다.

- [ ] 문서에 9개 장이 정해진 순서와 이름으로 존재합니다.
- [ ] 배경과 목적이 비개발자도 이해할 수 있게 작성됐습니다.
- [ ] 개선 사항 요약과 개선 상세의 번호가 일치합니다.
- [ ] 개선 사항에는 실제 변경 작업만 포함했습니다.
- [ ] 현재 동작과 문제점은 확인한 근거에 맞게 작성했습니다.
- [ ] 확인·추정·미확인 사항을 구분했습니다.
- [ ] 변경 대상과 작업 제외 범위를 명시했습니다.
- [ ] 테스트 시나리오와 통과 기준을 정의했습니다.
- [ ] 리스크와 대응 방안을 검토했습니다.
- [ ] Phase별 실행 순서와 승인 조건을 명시했습니다.
- [ ] 테스트 통과 기준과 전체 완료 기준을 구분했습니다.
- [ ] 본문 근거 번호와 References가 일치합니다.
- [ ] 불필요한 표·그림·반복 설명을 제거했습니다.
- [ ] 실제 수행하지 않은 작업을 완료로 표시하지 않았습니다.

**최종 원칙**

계획서는 무엇을 변경할 것인지 설명하는 문서이면서, 작업 범위를 통제하고 실행 결과를 검증하는 기준입니다.

**확인하지 않은 사실을 단정하지 않고, 승인받지 않은 변경을 수행하지 않으며, 검증하지 않은 결과를 완료로 판단하지 않습니다.**
