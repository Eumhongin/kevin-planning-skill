# 계획서 작성 (planning)

인자: 계획서 주제 또는 이름. 없으면 대화에서 주제를 정한다.

## 어느 규칙을 따르나

1. 작업 중인 프로젝트에 `.claude/rules/plan.md` 가 있으면 그 파일이 기준이다.
2. 없으면 이 스킬 폴더의 `rules.md` 가 기준이다. 9개 장 구성, 장별 작성 원칙, 승인 표, 용어 규칙이 들어 있다.

어느 쪽이든 규칙 내용을 이 스킬에 옮겨 적지 않는다. 아래 순서는 규칙을 적용하는 방법만 적는다.

## 순서

1. **규칙을 먼저 읽는다.** 위 「어느 규칙을 따르나」대로 고른 파일을 끝까지 읽는다.
2. **새로 쓸지 고칠지 정한다.** 같은 계획의 변경이면 기존 파일을 고치고 변경 일시·사유·승인 여부를 남긴다. 별도 작업이면 새 파일을 만든다. 위치는 규칙이 정한 곳(기본 `plans/yyyymmdd_hhmmss_계획서명.md`)이다.
3. **시각을 얻는다.** 아래 명령만 쓴다. Windows Git Bash 는 `TZ=Asia/Seoul` 이 UTC 로 나온다(2026-10-29 확인).
   ```
   TZ=KST-9 date +%Y%m%d_%H%M%S
   ```
4. **사실을 모은다.** 쓰기 전에 저장소에서 확인한다.
   - 현재 동작은 코드·로그·테스트 결과로 확인하고, 근거 위치(파일:라인, 커밋, 로그 경로)를 적어 둔다
   - 확인·추정·미확인을 나눠 둔다. 확인하지 않은 코드의 동작을 추론해 현재 동작으로 쓰지 않는다
   - 읽기·검색·분석만 한다. 코드 변경·설치·운영 프로세스 조작은 하지 않는다
5. **9개 장을 채운다.** 규칙의 장별 작성 원칙을 따른다. 특히 아래를 지킨다.
   - 1장 배경 및 목적: 비개발자도 읽는 평문. 코드 경로·함수 이름·커밋 해시·설정값을 쓰지 않는다
   - 2장 개선 사항 요약: 「~문제가 있어서, ~합니다」 한 문장씩. 저장소 변경만 넣고 운영 확인은 7장으로
   - 3장 개선 상세: 2장과 같은 번호. 근거는 본문에 `[n]`, 출처는 9장
   - 5장 통과 기준과 8장 완료 기준을 나눠 쓴다
   - 7장 Phase 1 첫 작업은 브랜치 생성(`~/.claude/rules/git.md`), 마지막 Phase 는 커밋 메시지 초안·케빈님 승인·finish
6. **점검한다.** 규칙의 「작성 전후 확인 사항」을 하나씩 본다. 그다음 아래를 문서에서 찾아 없앤다.
   - 「몸통」「시험」「고정」 같은 임의 번역어
   - 1·2장에 남은 경로·코드 이름
   - 줄표(`—`), 5열 넘는 표, `~합니다` 가 아닌 문장
   - 본문 `[n]` 과 9장 번호가 어긋난 곳
7. **커밋하고 보고한다.** 계획서 문서 커밋은 승인 예외라 바로 한다. push 는 하지 않는다. 보고는 계획서 경로·커밋 해시·결론 3줄, 그리고 승인받을 것(Phase 1 착수 등)이다.

## 하지 않는 것

- 계획서 없이 코드를 쓰거나 고치지 않는다. 계획서에 있는 것만 고친다
- 제목(#) 바로 다음에 작성 시각·작성 경위·규칙 안내 같은 머리말을 넣지 않는다. 바로 `## 1. 배경 및 목적` 으로 시작한다
- 9개 장의 순서·이름을 바꾸거나 장을 지우지 않는다. 해당 없으면 「해당 없음」과 이유를 쓴다
- 기존 계획서의 파일 이름을 바꾸지 않는다
- 계획서에 `(허락 필요)` 를 적었다고 승인받은 것으로 보지 않는다
- 실행하지 않은 테스트·검증을 완료로 체크하지 않는다
